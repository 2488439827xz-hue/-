# 双层评分与评测方案

## 为什么需要两套分数

候选排名回答“哪些仓库值得模型花时间看”，最终价值分回答“哪些项目值得用户花时间看”。把两者混成一个分数，会导致 Star、更新时间等易计算信号掩盖真正的产品价值。

## 第一层：确定性候选分（0–100）

由 `radar.py` 计算，仅用于预筛：

| 维度 | 上限 | 说明 |
|---|---:|---|
| 主题相关性 | 30 | Agent Skill > Agent > Workflow > 辅助主题 |
| 热度动量 | 20 | 优先使用本地快照 Star 增量；首次仅用代理并显式标注 |
| 维护活跃 | 15 | 最近 push 时间；归档项目为 0 |
| README 可用性 | 15 | 安装、用法、文档、测试、安全、License 信号 |
| 社区信号 | 10 | Stars 与 Forks 的对数缩放，不作为质量证明 |
| 新颖性 | 10 | 项目年龄，防止老项目永久霸榜 |

该分数不判断“问题是否重要”“是否适合用户”“是否能做作品集”。

## 第二层：AI 价值分（0–100）

每项 0–10，再按权重加权：

| 维度 | 权重 | 10 分含义 |
|---|---:|---|
| 个人相关性 | 25% | 直接服务 Agent/Skill/Workflow 学习与 AI PM 目标 |
| 问题价值 | 15% | 用户和痛点清晰、后果真实、方案值得存在 |
| 实用性 | 15% | 可安装、可运行、可复用，有清晰示例 |
| 独特性 | 10% | 相比替代方案存在可说明的机制差异 |
| 成熟度 | 10% | 维护、文档、许可、示例和社区较健康 |
| 学习价值 | 10% | 能学到可迁移的原理和实践 |
| 作品集价值 | 10% | 可形成可展示的分析、原型或改造方案 |
| 证据置信度 | 5% | 结论有充分、最新、可追溯的证据 |

公式：`最终分 = Σ(维度分 × 权重) × 10`。

## 热门与有价值为什么分开

- “热门”是注意力和传播结果，受项目年龄、作者影响力、发布事件和社区规模影响。
- “有价值”取决于问题、可用性、差异、风险和用户情境。
- 日报可以推荐一个高价值但 Star 较少的新项目，也可以拒绝一个高 Star 但停更或无法运行的项目。

## 初始评测集

正式运行前建立至少 24 个案例：

- 6 个高相关、高质量正例；
- 4 个高 Star 但低实用性反例；
- 4 个低 Star 但高潜力新项目；
- 3 个 Awesome/聚合仓库；
- 3 个停更、归档或 License 缺失项目；
- 2 个关键词相关但实际无关项目；
- 2 个 README 夸大或证据不足项目。

每个案例由人工标注：是否推荐、主要原因、严重风险、允许的 Star 原因表述。

## 评测指标

- **Top-5 有用率**：人工认为至少“未来有用”的比例。
- **覆盖率**：应推荐的项目进入候选和最终日报的比例，分两段测。
- **不受支持断言率**：无法从仓库证据支持的事实性断言比例。
- **关键风险召回率**：License、停更、不可运行等高风险是否被指出。
- **排序一致性**：相同输入重复运行时，核心项目是否稳定。
- **解释完整度**：八个必需分析字段是否齐全。
- **延迟与成本**：单次运行时长、API 请求量、模型消耗。
- **发送成功率**：飞书成功响应比例。

## 失败严重度

- S0：泄露 Webhook/Token、推荐恶意代码且鼓励直接运行——立即停用。
- S1：捏造项目能力或许可证、把 Star 原因假设写成事实——停止投递并修复。
- S2：项目相关性低、评分不稳定、遗漏重要风险——进入次日修复。
- S3：措辞、排版或轻微重复——常规优化。

## 线上监控与回滚

保留候选 JSON、评估 JSON 和最终 Markdown，确保每条推荐可追溯。若出现 S0/S1，暂停自动投递，退回“只生成本地报告 + 人工确认”的安全模式。提示词或评分规则更新后，用固定评测集回归，不能只看一份日报觉得“好像更好”。
