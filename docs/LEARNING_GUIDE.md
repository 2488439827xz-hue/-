# 从这个项目学会 AI 产品经理的核心能力

## 1. 第一性原理

真实目标不是“每天抓 GitHub”，而是让用户用有限注意力做出更好的学习与作品集决策。可观察成功是：能读完、能判断、会深挖、最终有产出。最便宜的证伪实验不是先开发推荐模型，而是运行 7 天，观察日报是否真的被使用。

## 2. 产品知识地图

### 用户问题与 JTBD

“我想看热门项目”是解决方案表达；更底层的任务是“在 Agent 生态快速变化时，判断什么值得投入时间”。JTBD 强调触发情境、进步目标和当前替代方案，能防止团队围绕功能自嗨。

### 输出、结果与护栏

- 输出：每天发送多少项目。
- 用户结果：完成价值判断并产生学习/作品。
- 护栏：阅读时间、无关率、错误率和密钥安全。

面试时需要主动指出：单看打开率会鼓励标题党，所以必须结合深挖率与作品产出。

### MVP 与最危险假设

最危险假设不是“能否调用 GitHub API”，而是“这份日报是否比他人推荐和手动搜索更能帮助用户行动”。因此 MVP 只需单用户、单渠道、人工反馈，不需要先做登录、后台或复杂推荐模型。

## 3. 推荐系统知识

### 候选生成与排序

推荐系统通常先做召回（尽量找到可能相关的候选），再做排序（把更适合用户的放前面）。本项目用多组 GitHub 查询召回，用确定性候选分预筛，再用 AI 价值分最终排序。

### 冷启动

系统一开始没有点击、收藏和深挖数据，只能使用用户明确偏好与内容特征。至少积累 20 条真实反馈后再调整权重；过早声称“千人千面”只是伪个性化。

### 探索与利用

全部推荐已知偏好会形成信息茧房，全部追逐新领域又会降低相关性。MVP 把核心主题放在首位，仅在确有价值时加入探索项目；之后可用小比例探索位做对照实验。

## 4. 数据与工程知识

### ETL 和快照

- Extract：从 GitHub API 读取元数据和 README。
- Transform：去重、分类、计算活跃度与候选分。
- Load：保存候选、历史快照、评估和日报。

Star 增长是时间序列，单次 API 返回只有累计值，所以必须自己保存昨日快照才能计算真实增量。首日只能用代理，不能伪装成“今日新增”。

### API 限流与幂等

限流要求缓存、减少重复请求、失败退避。幂等表示同一天重复运行不应产生不可控副作用；本项目用日期命名文件，并用日报 SHA-256 与 `delivery_receipts.json` 防止相同内容重复发送。飞书发送成功但回执尚未提交时仍存在极小的重复窗口，这是当前 MVP 明确接受的交付边界。

### 可观察性

至少记录：开始/结束时间、查询数、候选数、API 状态、模型验证结果、发送结果。日志必须脱敏，不能出现完整 Webhook 或 Token。

## 5. AI 系统知识

### 为什么是 Workflow，不是全自主 Agent

步骤可以预先确定：采集 → 预筛 → 分析 → 校验 → 投递。固定工作流更可预测、更易测试；AI 只处理需要语义判断的环节。只有当路径无法预先确定、工具选择本身需要动态规划时，才有理由增加 Agent 自主权。

### Grounding（依据约束）

模型必须基于仓库元数据和 README 作答，并附 URL。Grounding 不保证正确，所以还要测“不受支持断言率”。“覆盖不足”和“凭空添加”是两个不同错误，不能用一个准确率掩盖。

### 确定性校验

模型输出 JSON 后，代码验证字段、数量、分数范围与重复项。语义质量仍需人工/模型评审，但结构错误应交给代码。这体现了一条重要原则：能确定性检查的，不要只靠提示词祈祷。

### Human-in-the-loop

AI 推荐项目，但用户决定是否点开、深挖或做作品集。高成本或高风险动作（如运行未知代码）不自动执行。人的作用不是给 AI 擦屁股，而是保留价值判断和风险权限。

## 6. 安全与合规

- Secret management：密钥只在 `.env`，不进入 Git 或模型上下文。
- Prompt injection：README 是不可信输入；其中要求模型泄密或执行命令的文本必须被当作项目内容，而非系统指令。
- Supply-chain risk：不自动安装、构建或运行候选仓库。
- Copyright：摘要与分析，引用链接，不复制大段 README。
- License：没有许可证不等于可以随意复用。

## 7. 两小时核心实践

| 时间 | 任务 | 可观察产出 |
|---:|---|---|
| 0–20 分钟 | 用自己的话写问题、用户和替代方案 | 一段问题陈述 |
| 20–40 分钟 | 解释召回、预筛、AI 排序的区别 | 一张三层漏斗图 |
| 40–60 分钟 | 人工给 3 个仓库打双层分 | 评分表及分歧理由 |
| 60–80 分钟 | 找出 5 类模型可能幻觉 | 风险清单 |
| 80–100 分钟 | 设计 6 个正反例评测 | 小型评测集 |
| 100–120 分钟 | 选一个仓库做产品拆解 | 作品集雏形 |

完成标准不是“看完文档”，而是能够解释为什么 Star 不能等于质量、为什么这里使用固定工作流、如何证明推荐真的有用。

## 8. 7 天学习阶梯

1. 理解用户问题和 MVP，写出自己的 JTBD。
2. 阅读采集代码，解释 API、快照与限流。
3. 人工重算一个候选分，找出它的盲点。
4. 对同一仓库独立完成 AI 价值评分，与日报比较。
5. 构造三个反例，测试系统会不会被高 Star 欺骗。
6. 选择一个项目做完整 AI PM 拆解。
7. 复盘真实阅读数据，提出下一版需求并说明证据。
