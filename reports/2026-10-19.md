### 2. mvschwarz/openrig · 77.0/100
https://github.com/mvschwarz/openrig

- **一句话**：OpenRig 用 YAML 定义持久化的多智能体团队，把 Claude Code、Codex 等编码 Agent 作为有角色、有共享上下文、有任务归属的团队成员运行。
- **解决的问题**：多个编码 Agent 并行时往往依赖大量终端会话，缺少角色分工、持久上下文与统一协调方式。
- **独特之处**：不是再包一个模型，而是“包住多个 harness”，把多 Agent 当作可启动、可观察、可协作的团队系统。
- **为什么有价值**：对学习 Agent 编排与多智能体协作的产品经理很有参考价值：角色、上下文、任务归属与人工介入点都是关键设计变量。
- **与你的关系**：当下可用来理解多 Agent 编排模型；未来可借鉴其“角色+共享上下文+任务归属”设计，做 Agent 协作产品的原型或评估。
- **建议动作**：30 分钟内阅读 Getting Started 与 YAML 示例，用自己的一个开发任务画出团队角色与交接流程图，不实际安装。
- **Star 原因假设**：假设：多 Agent 编码是热点方向，支持信号是 topics 中 agent-orchestration 与 multi-agent；假设：项目提供可视化 TUI 与演示 GIF，降低理解门槛，可能带来传播；假设：近期约 133 Star/天的增长可能来自作者演示或社区讨论，但无直接证据
- **风险/限制**：依赖 Node.js 22/24 与 tmux，平台限制较多，Windows 仅支持 WSL2；自动化测试未覆盖 WSL2，且 issues 数量较多；多 Agent 并发调用的成本与安全边界需要实际评估
- **判断置信度**：medium

### 3. trevhud/rote · 73.0/100
https://github.com/trevhud/rote

- **一句话**：rote 把已验证的 Claude/Agent Skill 编译为类型化、确定性流水线，只在真正需要判断的步骤调用模型，从而降低 token 成本并支持回归测试。
- **解决的问题**：一个 Agent Skill 演示一次可行，但高频重复运行时成本高、结果不稳定、难以回归测试。
- **独特之处**：提出“Skill 编译”思路：把固定逻辑与工具编排移入可审阅代码，模型只负责需要判断的环节。
- **为什么有价值**：对 AI 产品经理理解从“Agent 演示”到“可运营工作流”的演进很有帮助，也涉及成本、确定性与评测三个核心指标。
- **与你的关系**：当下可用内置 expense-audit 示例理解 Skill 到流水线的转换；未来可借鉴“确定性优先、模型兜底”的设计原则。
- **建议动作**：30 分钟内运行 rote 的 expense-audit 示例，记录哪些步骤被编译为确定性代码、哪些仍调用模型。
- **Star 原因假设**：假设：token 优化与确定性工作流是当前 Agent 落地的痛点，支持信号是 README 标题与示例强调成本与可回归测试；假设：内置零 API 示例降低试用门槛，可能吸引开发者尝试；假设：Star 增长极低，说明尚未进入大众视野，更多是早期开发者关注
- **风险/限制**：Star 极少，社区验证与长期维护信号弱；README 未显示安全策略，编译后流水线的权限边界需自行评估；概念较新，学习曲线可能高于普通 Skill 工具
- **判断置信度**：medium-low

## 今日重点

重点看 trevhud/rote。它的目标用户是把 Agent Skill 用于重复业务流程的开发者与产品团队；待办任务是让已验证的 Skill 在高频运行时保持低成本、可预测、可回归测试。旧替代方案是每次让 Agent 在循环中重新推理，或手写脚本但失去 Skill 的可读性。价值主张是把固定逻辑与工具编排编译为确定性流水线，只在需要判断处调用模型。AI 并非全程必要，这恰是它的卖点：把不必要的模型调用降下来。核心指标可设为单次运行成本、端到端时延、成功率、回归测试覆盖率与人工复核率。主要风险是社区验证少、编译产物与原始 Skill 可能漂移、权限边界需自行确认。作品集衍生想法：选一个真实小流程，比较“纯 Agent 运行”与“rote 编译后运行”的成本、时延与失败模式，写成一页产品评估。
