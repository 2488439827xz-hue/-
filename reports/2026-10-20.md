## 今日项目

### 1. trevhud/rote · 77.0/100
https://github.com/trevhud/rote

- **一句话**：把已验证的 SKILL.md 技能编译成带类型、可回归测试的确定性流水线，只在需要判断的步骤调用模型。
- **解决的问题**：Agent 技能单次运行可行，但高频重复执行时 token 成本高、速度慢且结果不稳定。
- **独特之处**：提出“技能编译为流水线”的中间层思路，把固定逻辑和工具编排移入可审查代码。
- **为什么有价值**：它直接对应 AI 产品经理最关键的取舍之一：哪些步骤需要 LLM，哪些应降级为确定性代码，以及如何为 Agent 行为建立回归测试。
- **与你的关系**：当下可用 60 秒示例理解“LLM 步骤 vs 确定性步骤”的拆分方法；未来设计 Agent 成本模型与评测体系时，可复用其 IR 与回归测试思路。
- **建议动作**：运行 rote example expense-audit，打开生成的 pipeline 草案，标出哪些步骤保留了模型调用、哪些被固化；用 10 分钟写成一张“LLM 必要性判断表”。
- **Star 原因假设**：成本优化是 Agent 落地后的普遍痛点，可能吸引搜索流量；“无 LLM 循环”的反直觉定位带来传播；技能生态升温使 SKILL.md 相关工具获得发现机会
- **风险/限制**：Star 极少，社区验证与长期维护证据不足；需要理解 IR、运行时和 DBOS 等概念，学习曲线高于普通技能目录；编译后流水线的可维护性和边界条件仍需自行验证
- **判断置信度**：medium

### 2. mvschwarz/openrig · 75.8/100
https://github.com/mvschwarz/openrig

- **一句话**：用 YAML 定义由 Claude Code、Codex 等编码 Agent 组成的持久团队，包含角色、共享上下文、工作归属和 tmux 会话管理。
- **解决的问题**：多个编码 Agent 并行时，终端会话、上下文和产出散落，难以知道谁负责什么、哪些决策需要人接管。
- **独特之处**：把“Agent 团队”建模为可声明的配置与座位（seat），支持跨 harness 的角色分工和统一运行视图。
- **为什么有价值**：它把多 Agent 协作从 prompt 技巧变成可配置的组织结构，适合学习任务分配、上下文隔离和人工审批边界如何被产品化。
- **与你的关系**：当下可用于理解多 Agent 产品的角色/权限/上下文设计；未来做 Agent 工作流产品时，可借鉴其“持久团队 + 决策待办”的信息架构。
- **建议动作**：花 20 分钟读 docs/reference/getting-started.md，画出 starter 团队中的角色、共享上下文和人工介入点；再用 10 分钟写一页“多 Agent 协作产品最小信息架构”笔记。
- **Star 原因假设**：编码 Agent 用户对并行会话管理有真实痛点，Star 增长可能反映需求外溢；作者以“AI civilization 实验”叙事传播，带动早期关注；跨 Claude Code/Codex 的兼容性是当前开发者关注点
- **风险/限制**：依赖 Node.js 22/24 与 tmux，安装门槛对非工程背景读者偏高；多 Agent 长期运行的成本、错误传播和安全边界在 README 中说明有限；早期项目 API 与行为可能快速变化
- **判断置信度**：medium

### 3. apify/agent-skills · 69.5/100
https://github.com/apify/agent-skills

- **一句话**：Apify 官方的一组 Agent 技能，让编码 Agent 能选择并调用 Apify Actor 完成网页采集、Actor 构建和平台集成。
- **解决的问题**：Agent 需要真实网页数据时，往往缺少稳定、有明确输入输出契约的数据采集工具。
- **独特之处**：把 30,000+ Actor 的采集能力封装为 Agent 可发现和调用的技能，并提供 Actor 选择回退机制。
- **为什么有价值**：它是“工具型技能”的实用样本：有真实 API、明确输入输出、失败回退和平台配额，适合学习技能如何与外部服务契约结合。
- **与你的关系**：当下可参考其 SKILL.md 结构设计自己的工具型技能；未来做数据类 Agent 产品时，可借鉴 Actor 选择、回退与成本控制的产品模式。
- **建议动作**：读 README 的 Overview 与 Quick Start，选一个技能查看其输入输出定义，写一张“技能 → 外部 API → 失败回退 → 计费”的流程图。
- **Star 原因假设**：Apify 平台既有用户转化为 Star；网页采集是 Agent 高频需求，技能目录带来自然发现；官方背书提升信任度
- **风险/限制**：仓库元数据 license 为 null，使用前需核实实际许可；技能依赖 Apify 平台与账号/配额，非中立工具；README 营销表述较多，部分能力需实测
- **判断置信度**：medium

## 今日重点

重点项目：trevhud/rote。目标用户是把 Claude/Codex 技能用于重复业务流程的开发者与 AI 产品经理。待办任务是“同一技能每天/每月跑很多次，希望更便宜、更快、可回归测试”。旧替代方案是直接让 Agent 循环调用工具，或用传统脚本重写但丢失技能语义。价值主张是把技能拆成“固定逻辑 + 少量模型判断”，编译为可审查流水线。AI 是否必要：只在需要语义判断的步骤必要，固定规则和工具编排不应交给 LLM，这正是它的核心洞察。核心指标可设为单次运行成本、端到端时延、回归测试通过率、人工复核率。主要风险是项目极早期、概念门槛高、编译产物与上游技能变更的同步成本。作品集衍生想法：选一个你熟悉的重复流程（如报销审核或内容合规检查），画出“LLM 步骤 vs 确定性步骤”的决策表，并用 rote 示例的 IR 结构写出最小流水线草案。
