## 今日项目

### 1. NVIDIA/SkillSpector · 86.8/100
https://github.com/NVIDIA/SkillSpector

- **一句话**：面向 AI agent skill 的安全扫描器，检测漏洞、恶意模式、prompt injection、数据外泄与供应链风险，支持 Claude Code、Codex、MCP 等。
- **解决的问题**：Agent skill 以隐式信任执行，安装前缺乏统一的安全审查手段，用户无法回答“这个 skill 是否安全可装”。
- **独特之处**：71 个漏洞模式、17 类风险、两阶段静态 + LLM 语义分析，并接入 OSV.dev 实时 CVE 查询，把安全扫描做成可集成到发布流水线的门禁。
- **为什么有价值**：它是 agent skill 生态里少见的“验证层”产品，能帮助学习者理解 skill 安全的真实威胁模型与检查项，也是安全类作品集的现成脚手架。
- **与你的关系**：当下用途：用 SkillSpector 扫描一个你常用的 skill，阅读报告理解各风险类别。未来用途：在你的 Skill 发布流程中加入扫描门禁，并把这套指标写进产品需求文档。
- **建议动作**：30 分钟内按 README 安装 SkillSpector，扫描一个本地 skill 目录并输出 JSON 报告，记录 3 个最有价值的检查项。
- **Star 原因假设**：假设：NVIDIA 品牌背书与“26.1% 技能含漏洞”的量化结论形成强传播点，支持信号是 star_delta 约 121/天且 README 直接引用研究数据；假设：agent skill 安全是 2026 年的新空缺，先发者获得关注，支持信号是 topics 覆盖 agent-security、prompt-injection 等细分词；假设：可集成到 NVIDIA Verified Skills 流水线，使企业用户有采购/采用理由，支持信号是 Apache-2.0 与 OpenSSF Scorecard 徽章
- **风险/限制**：README 未展示测试覆盖，扫描器本身的误报/漏报率缺乏第三方验证；LLM 语义评估阶段可能引入额外成本与不确定性；依赖 NVIDIA 发布流水线，独立使用时的维护节奏不确定
- **判断置信度**：high

### 2. sickn33/agentic-awesome-skills · 86.5/100
https://github.com/sickn33/agentic-awesome-skills

- **一句话**：本地 agent-first 控制面，用于完整目录发现、agent 自主选择技能、stack 校验与计划生成，背靠 2,115+ agentic skills，含 CLI、本地 MCP、插件与 Workbench。
- **解决的问题**：Agent Skill 数量爆炸后，如何在不把选择权交给推荐算法的前提下，让 agent 从可信完整目录中选取精确技能，并在写入项目前完成校验与可审查计划。
- **独特之处**：明确把“推荐/排名”拿掉，改为 agent 自主选择 + 只读 compose_stack 内存校验 + 不可变 plan 预览，这种“agent 拥有选择权、工具只做验证”的定位在技能管理类项目中很少见。
- **为什么有价值**：对学习 AI 产品管理的人，这是一个可直接拆解的“控制面”案例：把目录、选择、校验、计划、人工审查分层，说明 agent 产品中信任与权限边界应该放在哪一层。
- **与你的关系**：当下用途：把 AAS Core 的 compose_stack 流程画成图，理解 agent-owned selection 与 read-only validation 的产品含义。未来用途：在你的 Agent 项目里复用这种“agent 选、工具验、人审”的三段式设计。
- **建议动作**：30 分钟内克隆仓库，运行 CLI 的 catalog 搜索并复现一次 compose_stack 校验输出，截图保存为流程图素材。
- **Star 原因假设**：假设：46k stars 主要来自 agent skills 话题的聚合效应与“2115+ skills”的规模感，支持信号是 topics 覆盖 20 个相关词且 star_delta 约 40/天；假设：AAS Core 从“技能集合”升级为“本地控制面”的新叙事吸引了早期采用者，支持信号是 README 强调 read-only MCP 与不可变 plan；假设：对 Codex/Claude 用户而言，一次性获得大量可发现技能降低了试错成本，支持信号是同时支持多个 harness 与插件安装
- **风险/限制**：README 自述“apply and recovery 仍为实验性”，说明核心写入路径尚未稳定；46k stars 与 2 周前创建时间差距大，存在初始热度或聚合推广可能，需二次快照验证；技能来源审计与长期维护治理在 README 中描述较少
- **判断置信度**：medium-high

### 3. first-fluke/oh-my-agent · 80.8/100
https://github.com/first-fluke/oh-my-agent

- **一句话**：多 agent harness，通过 artifact 校验 agent 是否真的完成工作：stop-hook 门禁、独立 judge、append-only 事件日志，兼容 Claude Code、Codex、Cursor 等 10+ 运行时。
- **解决的问题**：并行 agent 声称“测试通过、标准满足”不可证伪，同一会话内无法自证，导致交付质量不可信。
- **独特之处**：把 agent 的自我汇报变成可证伪的证据链：stop hook 拒绝结束直到项目自身脚本退出 0，gate 命令检查遗留 artifact，独立 judge 每轮重新验证。
- **为什么有价值**：这是 agent 可靠性方向少见的工程化方案，能帮助学习者理解 agent 评估中“证据 vs 叙述”的核心区别。
- **与你的关系**：当下用途：阅读其 gate 与 event log 设计，理解如何把 agent 的成功声明变成可审计证据。未来用途：在你的 Agent 项目里加入类似的完成门禁。
- **建议动作**：30 分钟内安装 oh-my-agent 并用一个示例项目跑一次 gate 命令，观察它如何拒绝假的“完成”声明。
- **Star 原因假设**：假设：多 agent harness 是热门话题，且“checks the work”的定位切中痛点，支持信号是 topics 覆盖 multi-agent-systems 与 orchestration；假设：跨 10+ 运行时兼容扩大了受众，支持信号是 README 展示多语言文档与 npm 安装；假设：独立 judge 与 append-only 日志提供了可演示的安全感，支持信号是 README 用 explainer 视频强化
- **风险/限制**：README 未展示测试信号，可靠性承诺需自行验证；依赖多个运行时适配，长期维护成本较高；1.3k stars 规模较小，社区验证有限
- **判断置信度**：medium

### 4. iflytek/skillhub · 79.5/100
https://github.com/iflytek/skillhub

- **为什么有价值**：对 AI 产品管理者，这是理解“技能治理”需求与产品形态的样本：当技能从个人收藏变成组织资产，需要哪些 registry 能力。
- **与你的关系**：当下用途：阅读其权限模型与审计日志设计，对照你所在团队是否有类似需求。未来用途：在设计内部 Agent 平台时，把 registry 与治理能力作为一期范围。

- **Star 原因假设**：假设：iflytek 品牌与企业 AI 治理话题带来关注，支持信号是 5k stars 与 enterprise-ai、ai-governance 等 topics；假设：自托管 + RBAC 解决了合规团队的顾虑，支持信号是 README 明确 Docker/K8s 部署与审计日志；假设：agent skill registry 赛道升温，资金与关注溢出到有企业背书的项目，支持信号是 first_run_proxy 排名与 Trendshift 徽章

## 今日重点

sickn33/agentic-awesome-skills：目标用户是同时使用 Codex/Claude 等 agent 运行时的开发者或产品经理，痛点是技能目录庞大但无法安全、可复现地选出一组精确技能。待办任务是“为一个具体项目挑选并固定一套可审查的技能集合”。旧替代方案是手动浏览 awesome 列表、复制 SKILL.md、靠记忆管理版本，容易漂移且无法审查。价值主张是 agent 自主从完整本地目录选择、由只读 compose_stack 校验、再生成不可变 plan 供人工审查。AI 必要性中等：选择可以由 agent 完成，但校验与计划必须由确定性工具完成，否则信任链断裂。核心指标可设为：校验通过率、plan 被人工接受率、技能栈漂移次数。主要风险是 apply/recovery 仍实验性、技能来源治理不足。作品集衍生想法：做一个“Agent Skill 选型审计”工具，输入 aas-stack.json 输出每个技能的风险与替代建议，展示你对 agent 治理链路的理解。
