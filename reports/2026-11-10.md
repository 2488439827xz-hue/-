# AI GitHub Radar · 2026-11-10

今天的候选集中在 Agent Skill 的安全、目录与治理三条线，整体质量中上，但真正适合 AI 产品经理在 30 分钟内动手的偏少。最值得看的是 NVIDIA/SkillSpector：它把“安装 skill 前先评估安全边界”变成可操作的产品问题，且证据最完整。paperclip 提供了多 Agent 团队治理的产品形态，适合观察工作流与权限设计，但 README 营销感重、文档信号弱，需要降权。sickn33/agentic-awesome-skills 与 zhuyansen/agent-skills-hub 都是目录型项目，前者体量大、可做技能检索对比，后者更偏内容农场式堆叠。intel/dokimi 与 agent-trace 规模小但问题定义清晰，适合判断“如何验证 skill 是否真的有用”，可作为方法论补充。今天不建议追逐 Star 增速，而应聚焦一个安全/治理项目做拆解。

## 今日项目

### 1. NVIDIA/SkillSpector · 85.0/100
https://github.com/NVIDIA/SkillSpector

- **一句话**：面向 AI Agent Skill 的安全扫描器，支持 Git 仓库、URL、压缩包、目录和单文件，覆盖提示注入、数据外泄、供应链与 MCP 滥权等风险；提供静态分析加可选 LLM 语义评估。
- **解决的问题**：Agent Skill 生态扩张快，但安装前缺乏统一的安全审查与信任门槛，用户很难判断某个 skill 是否会窃取数据、越权执行或注入恶意指令。
- **独特之处**：把“安装前安全体检”做成独立可运行的工作流，并提供 71 类漏洞模式、两阶段分析和 CVE 实时查询，而不仅是清单式推荐。
- **为什么有价值**：对 AI 产品经理来说，这是典型的“负向价值产品”：不直接提升生成能力，而是在 Agent 工作流中建立风险闸门。理解它的检测维度，能帮助你设计自己的 skill 准入策略和产品安全边界。
- **与你的关系**：当下用途：用一次扫描理解 skill 的风险分类，并把它作为你评估其他 skill 目录的前置检查。未来用途：如果你要为团队搭建 Agent 工具链，可参考它的规则分类设计内部 skill 审核清单或作品集案例。
- **建议动作**：在 30 分钟内，克隆仓库或按 README 安装后，对一个公开的 SKILL.md 或小仓库运行一次扫描，记录它报出的风险类别与报告中可读性最强的部分。
- **Star 原因假设**：NVIDIA 品牌背书与官方文档入口提升了可信度与传播效率；Agent Skill 安全问题在 2026 年成为实际痛点，扫描器填补了安装前审查空白；README 给出具体漏洞比例与多格式输入，降低了发现和试用门槛
- **风险/限制**：项目创建时间较新，长期维护与规则更新频率仍需观察；LLM 语义评估可能带来额外成本与结果波动，安全结论不宜完全自动化；扫描器不能替代人工审查，误报/漏报边界需要产品层明确
- **判断置信度**：high

### 2. sickn33/agentic-awesome-skills · 72.5/100
https://github.com/sickn33/agentic-awesome-skills

- **一句话**：包含 2,955+ 个可安装 SKILL.md 的技能库，覆盖 Claude Code、Codex、Cursor、Gemini CLI 等；AAS Core 支持本地目录检索、Agent 自主选择与计划预览。
- **解决的问题**：Agent Skill 数量爆炸后，用户很难发现、比较并审查适合自己技术栈的技能，安装过程也缺少可审阅的计划预览。
- **独特之处**：不只是技能清单，而是强调本地目录发现、Agent 自主选择和变更前计划预览，尝试把“选技能”做成可审查流程。
- **为什么有价值**：对 AI 产品经理，这是理解 Skill 生态供给侧的样本：技能如何分类、如何被 Agent 选择、如何避免盲目安装。
- **与你的关系**：当下用途：用它的目录结构观察技能分类法和典型 SKILL.md 结构，作为你写内部技能规范或评估清单的参考。未来用途：如果你想做技能推荐或选择类产品，可借鉴它的“计划预览”思路。
- **建议动作**：30 分钟内浏览 AAS Core 预览指南与 3 个不同类型 SKILL.md，记录它们共同的字段、触发条件和示例质量差异。
- **Star 原因假设**：技能数量大且覆盖主流编码 Agent，容易形成“一站式”印象；持续同步和版本化元数据提升了更新可见性；社区对 Claude Code / Codex skill 的高关注带来自然流量
- **风险/限制**：大量导入技能可能质量参差，许可证与归属需逐个确认；Apply 与 recovery 仍标注为实验性，端到端可用性有限；目录越大，发现质量越依赖排序和筛选设计
- **判断置信度**：medium

### 3. paperclipai/paperclip · 71.0/100
https://github.com/paperclipai/paperclip

- **一句话**：开源的多 Agent 团队管理应用，用 Node.js 服务端加 React UI 把多个 Agent 的目标、任务、成本、权限、技能和历史集中到一个仪表盘。
- **解决的问题**：团队使用多个 AI Agent 时，任务、权限、成本和上下文分散在不同工具里，缺少统一的工作台和治理视图。
- **独特之处**：把 Agent 编排从“单个助手”提升到“组织级任务管理”，强调按 Agent 分配模型、harness、权限和成本追踪。
- **为什么有价值**：对 AI 产品经理，它提供了一个可观察的产品形态：Agent 工作流的真正难点不只是提示词，而是任务分配、权限边界、成本可见性和跨会话状态。
- **与你的关系**：当下用途：阅读其任务与权限模型，提炼一张“多 Agent 工作台”的功能地图，用于竞品分析或需求文档。未来用途：可作为你设计内部 Agent 管理后台或作品集原型的参考架构。
- **建议动作**：30 分钟内只读 README 与文档中的权限、成本、任务模型部分，画出 5 个核心对象（Agent、任务、技能、权限、成本）的关系草图。
- **Star 原因假设**：“管理 Agent 的公司”这类类比容易传播，形成强记忆点；多 Agent 团队工作流是当下热门叙事，Star 增速可能受社交媒体与等待名单驱动；MIT 许可与可自托管降低了试用门槛
- **风险/限制**：README 营销表述较多，缺少明确文档信号，实际可用性需自行验证；Issue 数量很大，可能反映早期稳定性或支持压力；功能面广，30 分钟内难以真正跑通完整工作流
- **判断置信度**：medium

### 4. intel/dokimi · 70.0/100
https://github.com/intel/dokimi

- **一句话**：用 A/B 对照实验评估 skill、MCP 文档源、Agent 配置或仓库指南是否真的帮助编码 Agent；提供配对运行、通过/未通过评分和 p 值，并分析技能内容的新增、冗余与退化。
- **解决的问题**：Skill 和 Agent 指南很容易写得像有效，但缺少可证伪的对照实验来判断它们是否真的提升任务表现。
- **独特之处**：把“证明而非流行”作为核心主张，用同一套评估集做有无对照，并区分技能中哪些内容模型本来就会、哪些真正新增。
- **为什么有价值**：对 AI 产品经理，这是评估思维的训练场：如何定义任务、如何设置对照组、如何解释显著性，比看榜单更能提升判断力。
- **与你的关系**：当下用途：阅读它的四象限分析（新增、冗余、缺失、退化），用于审视你写过的提示词或 skill 文档。未来用途：如果你要做 Agent 效果评估或作品集实验，可借鉴它的对照设计。
- **建议动作**：30 分钟内只读 README 中的四象限图与一个示例，写出你自己一个 skill 或提示词可能落入的类别及验证方式。
- **Star 原因假设**：Intel 品牌与“证明而非流行”的强主张形成记忆点；Agent 评估是当下方法论缺口，容易吸引研究者与产品经理；项目较新，Star 增长更可能来自小众专业社区而非大众热度
- **风险/限制**：项目很新、Issue 很多，成熟度与稳定性有限；LLM-as-a-judge 评估本身存在偏差，p 值含义需要谨慎解读；缺少完整使用示例，30 分钟内难以跑通真实实验
- **判断置信度**：medium

### 5. zhuyansen/agent-skills-hub · 66.0/100
https://github.com/zhuyansen/agent-skills-hub

- **一句话**：对开源 Claude Skills、MCP Server 和 Agent 工具做安全分级与质量打分的目录，每 8 小时自动刷新，提供分类、对比和场景页。
- **解决的问题**：用户面对海量 skill 与 MCP 项目时，缺少带安全分级和质量信号的筛选入口。
- **独特之处**：把“安全分级 + 多维质量评分 + 场景化对比”做成持续更新的目录产品，而不只是静态 awesome list。
- **为什么有价值**：对 AI 产品经理，它展示了如何用信号工程给生态项目排序：分类、评分维度、刷新频率和对比页都是可借鉴的产品机制。
- **与你的关系**：当下用途：观察它的 10 维评分与安全分级如何影响排序，思考哪些维度真正影响你的选择。未来用途：可把它作为你设计内部技能市场或供应商评估表的参考。
- **建议动作**：30 分钟内打开目录站，挑两个同类 skill 使用对比功能，记录它给出的评分维度与你认为缺失的维度。
- **Star 原因假设**：安全分级与每 8 小时刷新提供了差异化叙事；目录类产品天然适合搜索引擎与话题标签带来长尾流量；Star 基数较小，增长可能更多来自目录内容而非代码质量
- **风险/限制**：评分方法透明度有限，质量分可能被营销化；安全分级若缺乏独立验证，容易形成虚假信任；项目以 HTML 为主，代码与数据管线可复用性待验证
- **判断置信度**：medium

## 今日重点

重点拆解 NVIDIA/SkillSpector。目标用户：使用 Claude Code、Codex 或 MCP 的个人开发者与小团队；他们会在安装第三方 skill 前犹豫，但缺少低成本的审查手段。待办任务：在把某个 skill 加入工作流前，判断它是否包含提示注入、数据外泄、供应链或 MCP 滥权风险。旧替代方案：人工阅读 SKILL.md、信任 Star 数或作者背书、直接安装后靠运气和事后排查。价值主张：把安全审查前置为一次可运行扫描，输出风险类别和证据，而不是给一个模糊的“可信”标签。AI 是否必要：静态规则和 AST 可以覆盖大量模式，LLM 语义评估用于补充规则难以表达的意图判断，因此 AI 是增强项而非唯一前提；产品价值在于把两者组合成可解释报告。核心指标：扫描完成率、高风险检出率、误报率、安装前拦截次数、从发现到报告的耗时。主要风险：规则更新跟不上攻击手法、误报导致用户忽略警告、把安全结论过度自动化。作品集衍生想法：做一页“Agent Skill 准入评估卡”，把 SkillSpector 的风险类别映射为产品经理可执行的 5 步检查清单，并附一个真实扫描报告截图与判读说明。
