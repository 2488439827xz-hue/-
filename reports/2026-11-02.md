# AI GitHub Radar · 2026-11-02

今天候选里真正值得 AI 产品经理花 30 分钟看的有两类：第一类是“Agent Skill 的安全与信任基础设施”，NVIDIA/SkillSpector 用 3 万+ 抽样数据给出 26.1% 技能含漏洞、5.2% 疑似恶意，直接把“装 skill 前要不要先审”变成一个可产品化的问题；第二类是“skill 之后的工作流编排层”，eddyy-skill-orchestrator 和 pstack-t3 都在解决多 skill/MCP 串联时的顺序、锚点、花钱/不可逆操作前确认问题，体量很小但概念对做产品设计很有启发。相反，agentic-awesome-skills、cherry-studio、tons-of-skills 属于体量大但差异化弱的目录/桌面客户端，学习收益主要来自观察它们的功能取舍而非深度。整体不是爆发级好日，建议把时间押在 SkillSpector 与一个编排类小项目上。

## 今日项目

### 1. NVIDIA/SkillSpector · 82.0/100
https://github.com/NVIDIA/SkillSpector

- **一句话**：面向 Claude Code、Codex、MCP 等 agent skill 的安全扫描器，支持仓库/URL/zip/目录/单文件输入，71 条漏洞模式，静态分析加可选 LLM 语义评估，输出终端、JSON、Markdown、SARIF。
- **解决的问题**：Agent skill 被当作隐式可信直接安装执行，但用户没有低成本手段判断“这个 skill 安不安全”，供应链风险与 prompt injection 都缺乏默认闸门。
- **独特之处**：把“装前扫描”做成可集成的分析管线（含 SC4 实时 CVE 查询与离线回退），并提供 NVIDIA Verified Skills 发布流程这一组织化落点，而不只是一个规则列表。
- **为什么有价值**：README 披露的 31,132 个 skill 样本中 26.1% 含漏洞、5.2% 疑似恶意意图，这个数字本身就是产品论证；对做 agent 产品的人来说，它示范了把“信任”做成产品功能而非文档承诺。
- **与你的关系**：当下用途：读它的漏洞分类（prompt injection、数据外泄、过度授权、MCP 工具投毒）来给自己产品的 skill/MCP 准入设计一份检查清单；未来用途：在自建 skill 市场上把它作为安装前的 CI 闸门或风险评分来源。
- **建议动作**：花 30 分钟 clone 仓库，对你自己或团队正在用的 2–3 个 skill 跑一次扫描，记录输出里哪几类风险和你的产品准入流程缺位，写成半页需求备忘。
- **Star 原因假设**：NVIDIA 品牌背书 + 与 Verified Skills 发布流程绑定，带来平台侧导流；主动蹭上 agent skill 供给链安全这一时间窗口，需求真实且此前无默认方案；48 天约 6,664 star 的增长与“26.1% 含漏洞”这类可引用统计的传播效应有关（假设，仅有 README 自述数据支持）
- **风险/限制**：README 中的 26.1%/5.2% 来自其自有研究数据集，采样与判定方法未在摘要中展开，不宜直接当行业基准引用；71 条模式偏规则驱动，误报/漏报率缺乏独立第三方评估；与 NVIDIA 托管目录绑定，存在平台锁定与供应商利益相关性问题
- **判断置信度**：high

### 2. yanmeng0113-ctrl/eddyy-skill-orchestrator · 69.0/100
https://github.com/yanmeng0113-ctrl/eddyy-skill-orchestrator

- **一句话**：一个 Agent Skill 形态的调度层：让 agent 先打印路线卡（route card），在派生步骤前锁定锚点（如角色设定），只在涉及付费或不可逆发布时暂停确认。
- **解决的问题**：多 skill / MCP 串联的真实失败往往很无聊：步骤顺序错、派生内容漂移、付费渲染或发布在没人点头前就触发。多数编排框架没有把“何时必须停下来问人”显式建模。
- **独特之处**：把编排拆成三个可检查的机制——路线卡、锚点锁定、成本/风险闸门——而不是再做一个流程引擎；并且它以单个 SKILL.md 分发，几乎零安装成本。
- **为什么有价值**：对 AI 产品经理来说，这是一个很具体的“人机确认边界”设计样例：哪些步骤可以自动，哪些必须阻塞在人的同意上，以及如何让 agent 在执行前把计划说清楚。
- **与你的关系**：当下用途：拿它的 route card 模板改造你正在做的 agent 流程，定义自己产品的“必须确认节点”；未来用途：如果要做面向创作者或运营的自动化流水线，这套成本闸门 + 锚点锁定的模式可直接复用为交互设计基线。
- **建议动作**：30 分钟内把 SKILL.md 里的路线卡模板抄下来，用你自己产品的一条真实多步流程（例如“生成素材→审核→发布”）填一遍，标出哪一步应该被 cost_confirm 或 high_risk_confirm 阻塞。
- **Star 原因假设**：解决的是多 skill 串联的高频痛感，概念易懂、一句话能讲清；以 npx skills add 与多宿主目录自动探测降低试用门槛；仅 1 star，热度几乎不存在；其价值在于概念清晰而非传播（非热度驱动假设）
- **风险/限制**：几乎零社区验证（1 star、0 fork），作者维护可持续性未知；收益高度依赖宿主 agent 是否遵守 SKILL.md 里的软约束，没有硬性执行保障；README 示例以视频渲染流水线为主，跨场景泛化能力尚未被证据支持
- **判断置信度**：medium

### 3. ryuxdsgn/design-intelligence · 68.5/100
https://github.com/ryuxdsgn/design-intelligence

- **一句话**：给 agent 的设计技能：先问清产品上下文再动手，未知信息不编造（不虚构费用、促销、政策），为失败态设计，并解释每个决策；通过 npx 分发，兼容多种 agent。
- **解决的问题**：AI 生成界面时常见的失败是“先画后想”：编造业务事实、忽略异常态、无法说明设计理由，导致产出不可评审。
- **独特之处**：把“先理解再设计”固化为技能内的强制对话流程，并提出 DESIGN.md 作为产品上下文载体；这是对生成式 UI 工具链缺失的一层约束。
- **为什么有价值**：对 AI 产品经理，它给了一个可复用的原则：把不确定性显式化（问、而不是编），并把设计决策变成可追溯产物。这个思路可迁移到任何 agent 产品。
- **与你的关系**：当下用途：借鉴它的“先问再生成 + 不虚构未知业务信息”规则，写进你产品里生成类功能的系统提示约束；未来用途：如果做面向设计的 agent 工具，DESIGN.md 这种上下文文件可作为产品设计文档的一种新形态。
- **建议动作**：30 分钟内跑通一次 npx @ryuxdsgn/design-intelligence，用一句话描述一个小功能，观察它问了哪些问题、在哪些点停下而不是编造，记录成你的“生成前澄清清单”。
- **Star 原因假设**：切中生成式 UI“看起来很行、评审时全是编造数据”的痛点；npx 一行启动 + 多宿主兼容，试用摩擦极低；78 star 的低基数说明目前主要靠口碑而非规模传播（假设）
- **风险/限制**：小团队/个人项目，维护与长期路线未知；实际产出质量高度依赖下游 agent 与设计工具（如 Figma）的连接能力，README 展示偏理想流程；‘不编造’属于软约束，缺少可验证的度量方式
- **判断置信度**：medium

### 4. creedants/pstack-t3 · 61.5/100
https://github.com/creedants/pstack-t3

- **一句话**：把 Lauren Tan 的 pstack 技能集移植到 T3 Code，并加入 brigade：每项目一个常驻协调者，每个工作单元在独立 git worktree 跑，尽量让另一模型家族审 commit，再经队列合并入主干。
- **解决的问题**：多模型协作写代码时，缺少“谁有权改主干、改动如何被独立复核、并行任务如何不互相踩”的结构化约束。
- **独特之处**：把 code review 的“另一个模型家族”与 worktree 隔离、单一写入者合并队列绑在一起，形成一条可审计的落地路径，而不只是提示词层面的 multi-agent。
- **为什么有价值**：它展示了 agent 工作流里最容易被忽略的工程边界：并发写、合并权限、独立复核。对设计 agent 协作产品的人，这是很好的反面清单来源。
- **与你的关系**：当下用途：读它的工作单元→worktree→复核→合并队列结构，用它来审视你自己 agent 流程的“谁能写、谁来复核”问题；未来用途：若要做团队级 agent 平台，这套隔离与合并闸门可作为架构参考。
- **建议动作**：30 分钟内只读 docs/how-it-works.md 与合并队列那一节，画一张“一个任务从请求到落主干”的时序图，标注你产品里缺失的复核或阻塞点。
- **Star 原因假设**：背靠知名作者 pstack 的方法论，吸引关注其技能集的人；多模型互相 review 的话题性强，但项目本身声量很小；热度低（17 star），说明它更像小众移植实验而非被验证的产品（假设）
- **风险/限制**：17 star、极小社区，实际可用性基本未经验证；依赖 T3 Code 0.1.3+ 与特定宿主，迁移成本与可持续性存疑；README 信息密集但入口分散，30 分钟内只能理解结构，难以真正跑通
- **判断置信度**：medium

### 5. sickn33/agentic-awesome-skills · 61.0/100
https://github.com/sickn33/agentic-awesome-skills

- **一句话**：2,884+ 个可安装 SKILL.md 的库，AAS Core 支持本地目录检索、由 agent 自行选技能并预览变更计划；明确不排序、不推荐，apply 与恢复仍属实验性。
- **解决的问题**：skill 数量爆发后，用户既找不到也管不住“我到底装了哪些技能”，安装行为缺乏可审查的中间态。
- **独特之处**：卖点不在 skill 数量，而在 AAS Core 的“agent 自选 + 计划预览 + 信任边界声明”，把安装变成一个可审查的过程。
- **为什么有价值**：它示范了目录型产品的差异化方向：不做推荐榜单，而做可审计的装配流程。对设计 skill 市场的人来说，这是一条与“大而全榜单”相反的路线。
- **与你的关系**：当下用途：观察它如何用“计划预览 + 明确不排名”来回避推荐责任与质量争议，作为你自己做目录/市场时的产品取舍参考；未来用途：AAS Core 的 agent-owned selection 模式可作为你产品里“让 agent 自己配工具”的交互原型。
- **建议动作**：30 分钟内只读 AAS Core 预览指南那一段，列一张“预览计划里应包含哪些字段才能让人放心点应用”的清单，与你自己产品的确认弹窗对比。
- **Star 原因假设**：skill 目录 + 大数量 + 多宿主关键词覆盖面广，天然吃搜索流量；README 首屏给出可安装与探索入口，转化路径短；约 4.9 万 star 与 2,884 个 skill 的体量互为背书，存在规模即信任的认知偏差（假设）
- **风险/限制**：核心的 apply/恢复仍为实验性，宣称与可用性有差距；技能数量不等于质量，README 自述不排序，选型责任实际转嫁给用户；独立社区项目但大量使用厂商名称描述兼容性，需注意关联性误解
- **判断置信度**：medium

## 今日重点

NVIDIA/SkillSpector。目标用户：正在把 Claude Code / Codex / MCP 技能接进工作流的开发者与团队负责人。待办任务：在装一个第三方 skill 之前，用低摩擦方式回答“它安全吗、它会不会读我的密钥、会不会偷偷发网络请求”。旧替代方案：人工读 SKILL.md、凭作者口碑、或者干脆不审直接装——在 3 万级 skill 供给下这些方案都不可扩展。价值主张：把隐式信任变成可检查的安装闸门，输出结构化报告（JSON/SARIF）以便接进 CI。AI 是否必要：部分必要——静态规则可以覆盖大部分模式，但语义级判断（这段指令是否在试图越权、是否在诱导模型外泄数据）需要 LLM 评估，这也是它做成两阶段分析的原因；如果只有规则，误报会劝退用户。核心指标：安装前扫描覆盖率、报告被真正用于阻断安装的比例、误报率、以及从发现到修复的时长。主要风险：自有数据集得出的 26.1% 缺乏外部复核，容易被当成行业事实引用；规则库对新型攻击的滞后；与 NVIDIA 目录绑定的中立性质疑。作品集衍生想法：做一个“skill 准入评分卡”小产品原型——输入一个 SKILL.md，输出权限请求、外部网络调用、可触发副作用三张卡片加一个放行/阻断建议，并把 SkillSpector 的报告作为其中一栏数据源，重点展示你如何把安全信号翻译成非安全背景产品经理能做的决策。
