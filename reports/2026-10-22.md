# AI GitHub Radar · 2026-10-22

今天这批候选整体集中在“Agent Skill 目录/注册中心”这一类，真正能帮助 AI 产品经理理解 Agent 工作流设计的项目不多，质量偏中等。最值得看的是 agentic-awesome-skills：它同时呈现了“技能库的发现、选择和变更前预览”这一产品化问题，规模大、文档和边界写得清楚，适合用来学习 Agent 能力供给层的产品设计。openrig 与 oh-my-agent 值得作为“多 Agent 编排”的两个对照样本：前者偏“持久团队与运行时编排”，后者偏“角色/工作流/技能的可移植封装”，两者都适合转化为流程图和作品集。pi-agent-dashboard 与 rote 是补充视角：前者说明多会话 Agent 的可观测性需求，后者提出“把成熟技能编译成确定性管线”的成本与可靠性思路，但后者 Star 极高可信度低、生态冷启动弱。目录/注册中心类的 agent-skills、skills、skillsmith 等存在同质化和营销表述偏多的问题，今天不建议优先投入。Star 增速只是发现线索，不能当作质量证明。

## 今日项目

### 1. sickn33/agentic-awesome-skills · 80.0/100
https://github.com/sickn33/agentic-awesome-skills

- **一句话**：一个包含 2,700+ 个可安装 SKILL.md 的技能库，配套本地 AAS Core：让 Agent 搜索本地目录、记录自己选择的技能、校验技能栈，并在改动目标前预览计划。
- **解决的问题**：Agent 技能数量爆炸后，用户很难知道有哪些技能、某个技能具体包含哪些文件、安装后会改动什么，缺少“可检查、可回滚”的选择与预览流程。
- **独特之处**：不只做技能目录，而是把“Agent 自己选技能”和“改动前预览计划”做成受控流程，并明确自己不做排名推荐，边界相对诚实。
- **为什么有价值**：它把 Agent Skill 当作有安装副作用的产品资产来治理，涉及发现、信任、变更预览与恢复，这些都是 AI 产品经理会真实面对的决策点，而不是简单的 awesome-list。
- **与你的关系**：当下：用它理解 Skill 目录的产品结构、SKILL.md 的字段与安装信任边界。未来：做 Agent 能力市场或内部技能库时，可复用其“选择—校验—预览—应用”的状态机思路。
- **建议动作**：30 分钟内挑 3 个不同领域的 SKILL.md（如研究、编码、文档），对比它们的触发条件、输入输出和失败处理，画一张“技能被选中到应用”的时序草图。
- **Star 原因假设**：假设：多个编码 Agent（Claude Code、Codex、Cursor、Gemini CLI）同时支持 SKILL.md，产生跨工具安装需求，带来集中关注。支持信号：topics 与 README 徽章覆盖多个 Agent 客户端；假设：2,600+ 技能的目录规模本身形成“先收藏备用”的星标动机。支持信号：README 强调本地完整目录检索与技能数量；假设：高 Star 也可能来自目录型仓库的传播效应，而非实际安装使用率。支持信号：README 自述 apply 与 recovery 仍属实验性
- **风险/限制**：apply 与 recovery 仍标注为实验性，真实安装回滚能力可能不足；规模大但质量参差，目录本身不做排名推荐，选到低质量技能的筛选成本高；“独立社区项目”与多个厂商名称并置，容易让读者误判官方背书关系
- **判断置信度**：high

### 2. first-fluke/oh-my-agent · 75.0/100
https://github.com/first-fluke/oh-my-agent

- **一句话**：面向已有编码 Agent 的厂商无关 harness，提供 12 个角色、21 个工作流、33 个技能，由 planner 拆解、工程师并行构建、reviewer 检查、debugger 修根因，并在长流程中用测试门禁回退。
- **解决的问题**：单个编码 Agent 缺少稳定的角色分工与工作流约束，复杂任务容易跳过规划、跳过验证，产出难以审计。
- **独特之处**：把角色、工作流、技能分层封装，并强调“步骤留下文件”和“等待你自己的 test/lint 通过”的门禁，跨 14 个以上 Agent 客户端复用。
- **为什么有价值**：它展示了 Agent 工作流产品化的关键取舍：流程固化到什么程度、门禁用谁的标准、产出物如何变成可审查的文档，这比单纯堆技能更有学习价值。
- **与你的关系**：当下：学习 12 角色/21 工作流的组织方式与文件化产出设计。未来：设计内部 Agent 工作流平台时，可借鉴其角色—工作流—技能三层与测试门禁。
- **建议动作**：30 分钟内读架构图与一个工作流定义，写出“规划—构建—审查—调试”每一步的输入、产出文件和失败回退条件。
- **Star 原因假设**：假设：跨多客户端（Claude Code、Codex、Cursor 等）的统一 .agents/ 目录解决了用户换工具后的迁移焦虑。支持信号：topics 与 README 均强调 vendor-agnostic 与多客户端支持；假设：测试门禁与文件化产出迎合了团队对可审计性的需求。支持信号：README 明确 gate 等待自有 test/lint/typecheck
- **风险/限制**：角色与工作流数量多，实际效果依赖具体 Agent 客户端能力，缺少统一评测；安装脚本为 curl | bash 形式，供应链风险需要自行评估；无安全信号，生产环境使用前需自查权限与数据流
- **判断置信度**：medium

### 3. mvschwarz/openrig · 73.5/100
https://github.com/mvschwarz/openrig

- **一句话**：用 YAML 定义由 Claude Code、Codex 等 harness 组成的持久 Agent 团队，一条命令启动，通过 lead agent 协调专家、共享上下文并保留工作现场。
- **解决的问题**：编码 Agent 往往散落成多个终端会话，角色、上下文和工作归属没有统一结构，难以把一次性对话变成有组织的持续协作。
- **独特之处**：把“harness 包模型”再往上抽象成“rig 包 harness”，强调持久团队、角色座位和共享地址，而不只是单次多 Agent 调用。
- **为什么有价值**：它把多 Agent 协作的产品问题显性化：谁是 lead、任务如何分配、上下文放在哪、结果如何回流给人。这些是设计 Agent 工作流时必须回答的结构性问题。
- **与你的关系**：当下：学习 YAML 定义 Agent 团队与角色分工的表达方式。未来：设计企业内多 Agent 协作产品时，可借鉴其“座位+共享上下文+人工接管”的模型。
- **建议动作**：30 分钟内读 quickstart 与 YAML 示例，画出“用户→lead agent→专家 agent→结果回流”的信息流，并标注哪些环节需要人工审批。
- **Star 原因假设**：假设：多 Agent 编排是当前编码 Agent 用户的高频痛点，仓库正好给出可运行的一体化方案。支持信号：topics 覆盖 agent-orchestration、multi-agent-systems；假设：作者以“AI civilization 实验”叙事和个人 X 账号传播带动关注。支持信号：README 引用个人实验与社交关注入口
- **风险/限制**：无测试信号，编排层复杂，边界情况可靠性存疑；open_issues 166 且更新频繁，项目仍处快速变动期，API 可能不稳定；多 Agent 长时运行涉及成本与权限扩散，README 对安全边界的说明有限
- **判断置信度**：medium

### 4. trevhud/rote · 69.0/100
https://github.com/trevhud/rote

- **一句话**：把已经验证过的 Claude/Agent Skill 编译成带类型、确定性的流水线，固定逻辑与工具编排变成可审查代码，只在真正需要判断的步骤调用模型，可做回归测试。
- **解决的问题**：一个 Skill 手工跑一次没问题，但重复运行上千次时，LLM 在环导致成本高、耗时长、结果不可回归测试。
- **独特之处**：提出“编译技能”而非“运行技能”的思路：把固定流程沉淀为确定性代码与 IR，模型只保留判断型步骤，并支持 emit 成普通 Python 脚本。
- **为什么有价值**：它触及 Agent 产品化的核心权衡：哪些步骤必须用模型、哪些可以固化以降低成本与不确定性。这种“按需用 AI”的判断力对产品经理非常关键。
- **与你的关系**：当下：用内置 expense-audit 示例理解“技能→IR→确定性管线”的转化过程。未来：设计高重复量 Agent 流程时，可借鉴其“确定性优先、模型兜底”的成本模型。
- **建议动作**：30 分钟内运行 rote example expense-audit 并 emit 出 Python 脚本，对照 SKILL.md 标出哪些步骤变成了代码、哪些仍调用模型。
- **Star 原因假设**：假设：token 成本与确定性是 Agent 规模化的真实痛点，概念吸引开发者关注。支持信号：README 以“跑一千次”作为核心叙事；假设：Star 仅 8，说明概念尚未被广泛验证，传播主要靠话题标签。支持信号：stars_per_day 为 0，社区信号极弱
- **风险/限制**：Star 与社区信号极弱，缺少外部使用验证；“编译技能”对 SKILL.md 结构有隐含要求，适用范围可能有限；无安全信号，生成代码的执行权限需谨慎管理
- **判断置信度**：low

- **风险/限制**：强绑定 pi 单一生态，换 Agent 后不可复用；开放端口与隧道远程控制带来安全暴露面，需自行加固；open_issues 33 相对 Stars 偏高，稳定性待观察

## 今日重点

重点看 sickn33/agentic-awesome-skills。目标用户：同时使用 Claude Code、Codex、Cursor 等编码 Agent 的开发者与内部平台团队。待办任务：在大量 SKILL.md 中找到可用技能，确认它包含哪些文件、安装后会改动什么，并保留可回滚的技能集。旧替代方案：awesome-list 加手动 git clone，或凭搜索结果直接安装，缺少统一的选择记录与变更预览。价值主张：把技能当作需要治理的安装包，提供本地目录检索、Agent 自主选择、技能栈校验和计划预览，并明确自身不做排名推荐。AI 是否必要：目录检索与预览本身可以确定性实现，AI 的价值在于让 Agent 根据任务自主挑选技能并解释选择理由，因此是“辅助判断”而非“替代治理”。核心指标：技能选择后被实际应用的比例、预览到应用的转化率、应用失败与回滚率、用户选中技能的复用率。主要风险：apply/recovery 仍实验性；技能规模大导致质量参差；社区项目与厂商名称并置可能引发背书误读。作品集衍生想法：做一个“Agent 技能供应链看板”原型，展示技能来源、版本、被哪些 Agent 选中、安装影响面与回滚记录，用一页流程图讲清信任边界。
