### 2. qufei1993/skills-hub · 77.0/100
https://github.com/qufei1993/skills-hub

- **一句话**：Skills Hub 是一个 Tauri + React 跨平台桌面应用，把 Agent Skills 集中安装到一个中央库，再按全局/项目范围同步到 Claude Code、Codex、Cursor、OpenCode、Antigravity 等多个工具的 skills 目录，优先 symlink/junction、必要时回退到拷贝。
- **解决的问题**：同一份技能被复制到多个 AI 编码工具的目录，来源、更新状态和启用状态漂移，手工清理成本高，多台设备之间更难保持一致。
- **独特之处**：用“中央库 + 多工具同步 + 多设备同步（通过 Git 仓库）”的方式解决技能分发碎片化，并提供回收站、标签、批量操作等真正的管理 UI，而非又一个命令行安装器。
- **为什么有价值**：它暴露了 Agent 生态的一个真实工程问题——工具各自为政的技能目录。把这个问题产品化为桌面应用，是很好的“从痛点出发”的产品案例，也便于观察多工具同步的产品权衡（symlink vs copy、全局 vs 项目）。
- **与你的关系**：当下：看它的 Why Skills Hub 与 Key Features，梳理“一个技能在多工具间分发”的需求清单。未来：如果你做 Agent 工具链产品，这是很好的竞品/参照；也可以做一个“技能同步冲突可视化”的小作品集模块。
- **建议动作**：30 分钟内在本地安装并打开 Skills Hub，把 2–3 个技能同步到两个不同工具目录，记录同步过程里让你困惑或觉得多余的一步。
- **Star 原因假设**：假设：多 Coding Agent 并存造成目录管理痛点，引起真实需求；支持信号：README 明确列出 Claude Code、Codex、Cursor、OpenCode、Antigravity 等多个目标工具；假设：桌面 GUI + Tauri 的小体积体验降低了使用门槛；支持信号：项目使用 Rust + Tauri，topics 含 desktop-app，readme 有截图与界面预览章节；假设：多设备库同步（Git 托管）对多机开发者有吸引力；支持信号：Key Features 中单独列出 Multi-device library sync 并说明支持 GitHub/GitLab/Gitee
- **风险/限制**：依赖具体工具的 skills 目录约定，上游工具改路径或格式时会失效，需跟随更新；symlink/junction 在不同操作系统和权限模型下行为有差异，回退到 copy 后同步状态可能出现不一致；Tauri 桌面应用分发与自动更新对非技术用户仍有门槛，readme 有安全信号但缺少 tests 证据
- **判断置信度**：medium

## 今日重点

重点看 sickn33/agentic-awesome-skills。目标用户：同时使用多个 Coding Agent、已经积累几十上百个技能、开始担心技能重复与不可复现的开发者与 AI 产品经理。待办任务：在真实项目里装配一组可解释、可审查、可回溯的技能集合，而不是随手复制几个 SKILL.md。旧替代方案：手工维护目录清单、在不同工具间拷贝技能文件夹、靠记忆判断哪些技能适用；结果往往是不可复现，也说不清为什么装了这些技能。价值主张：AAS Core 把“选择”留给 Agent，把“校验”做成只读工具，把“变更”拆成一个不可变的计划先给人看——不是替用户决策，而是提供可审计的装配协议。AI 是否必要：是。技能数量到千级后，人工匹配项目与技能的边际成本过高，Agent 的检索与匹配是必要的；但关键在于把高风险动作留给人类审批，这也正是它把 apply 标为 experimental 的原因。核心指标：一是从“项目 → 选定技能 → 计划生成”的成功率与耗时，二是生成计划被人类接受/修改/拒绝的比例，三是同一项目重复装配时的选择一致性。主要风险：目录膨胀导致技能质量参差；只读校验之外的实际变更路径仍是实验性；本地 MCP 与各 Coding Agent 的兼容性会随上游变化漂移。作品集衍生想法：做一个“技能装配差异器”——对同一项目给两组不同技能的 aas-stack，可视化它们的技能重叠、冲突与理由，并用一个小型 benchmark 展示哪组在真实任务上表现更好。
