## 今日项目

### 1. mvschwarz/openrig · 76.0/100
https://github.com/mvschwarz/openrig

- **一句话**：用 YAML 定义多 Agent 团队，把 Claude Code、Codex 等 harness 包装成持久化、有角色分工的编排系统，单命令启动。
- **解决的问题**：多个编码 Agent 分散在终端会话里，难以共享上下文、分配职责和追踪产出。
- **独特之处**：把‘harness 包 harness’抽象成 rig，用配置而非代码描述团队结构与协作。
- **为什么有价值**：对学习 Agent 编排的产品经理来说，它是一个可读的‘多 Agent 组织设计’样本，展示角色、上下文与交接如何被产品化。
- **与你的关系**：当下可用来理解多 Agent 团队的产品抽象；未来做协作型 Agent 产品时，可借鉴其角色与上下文寻址的设计。
- **建议动作**：花 20 分钟读 quickstart 与 YAML 示例，画出 rig 的角色/上下文/交接图，写 100 字它与单 Agent 的差异。
- **Star 原因假设**：多 Agent 编排是当前高关注主题，容易获得传播；开源‘AI 文明实验’叙事吸引对自主 Agent 感兴趣的开发者
- **风险/限制**：无测试信号，复杂编排的正确性难以从证据判断；多 Agent 系统调试成本高，初学者易被复杂度劝退
- **判断置信度**：中

### 2. upex-galaxy/agentic-qa-boilerplate · 73.8/100
https://github.com/upex-galaxy/agentic-qa-boilerplate

- **一句话**：基于 Playwright + TypeScript 的 QA 样板，把测试规划、迭代测试、用例文档、自动化与回归签核拆成多个 Agent Skill。
- **解决的问题**：QA 流程长且碎片化，测试计划、用例、自动化与发布判断之间缺少可复用的 Agent 工作流。
- **独特之处**：按 QA 生命周期组织 skills，并用 GO/NO-GO 把结果变成可决策的产物。
- **为什么有价值**：是‘把领域流程拆成 Agent Skill’的清晰案例，可直接对照学习任务分解与产出定义。
- **与你的关系**：当下可研究它如何把 QA 阶段映射为 skills；未来做垂直工作流产品时，可复用这种阶段化拆解方式。
- **建议动作**：用 30 分钟浏览 skills 目录，列出每个 skill 的输入/输出，并标出哪一步最依赖人工判断。
- **Star 原因假设**：QA 自动化与 Agent 结合是明确痛点，易被测试团队转发；样板式仓库便于直接试用，传播门槛低
- **风险/限制**：Star 少、社区信号弱，长期维护不确定；无安全相关信号，接入真实测试环境前需自行评估
- **判断置信度**：中低

### 3. ATASTECH/pitroom · 69.2/100
https://github.com/ATASTECH/pitroom

- **一句话**：让主 Agent 负责决策，把阅读、修复、测试、评审分发给更便宜的并行 worker，并返回答案、diff 与回执。
- **解决的问题**：昂贵的编码 Agent 大量 token 花在阅读和机械操作上，成本高效率低。
- **独特之处**：以‘主 Agent 决策 + 廉价 worker 执行 + 第二模型评审’的成本分层设计为核心卖点。
- **为什么有价值**：提供了 Agent 工作流中‘成本-质量分层’的产品思路，适合学习如何用产品设计控制推理成本。
- **与你的关系**：当下可研究其 worker 适配与回执机制；未来设计 Agent 产品时，可借鉴成本分层与证据回传。
- **建议动作**：用 30 分钟读 workflow 与 backends 文档，画一张‘决策/执行/评审’三角色流程图并标注成本假设。
- **Star 原因假设**：‘降低 Agent 成本’是强需求，容易引发共鸣；多 CLI worker 兼容扩大了受众
- **风险/限制**：首次快照代理，增长数据不可靠；并行 worker 的输出质量与一致性缺乏独立验证
- **判断置信度**：低

## 今日重点

重点看 openrig。目标用户：同时使用多个编码 Agent 的开发者与小团队；待办任务：让多个 Agent 共享上下文、按角色分工并持续产出可审查的改动。旧替代方案：手动开多个终端会话、复制粘贴上下文、人工协调交接。价值主张：用 YAML 把‘Agent 团队’变成可启动、可寻址的系统，降低协调成本。AI 是否必要：是，核心价值来自多 Agent 的并行与分工；但若任务简单，单 Agent 更划算。核心指标：首个有效改动的完成时间、人工接管次数、跨 Agent 上下文丢失率。主要风险：复杂度与调试成本高，缺少测试信号，团队规模扩大后状态一致性难保证。作品集衍生想法：做一页‘单 Agent vs 多 Agent 团队’的决策对照图，用 openrig 的角色模型说明何时值得引入多 Agent，并附成本与接管次数假设。
