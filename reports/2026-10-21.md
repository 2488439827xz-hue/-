# AI GitHub Radar · 2026-10-21

今天的候选不是热搜拼盘，而是两类清晰可学的方向：一是“Agent 技能生态的目录与治理”（AAS Core、NVIDIA Skills、QA Skills、Awesome 清单），二是“把 Agent 工作流工程化”（OpenRig 的多智能体团队、Brigade 的跨工具证据与记忆、Project Swarm 的并发编排）。其中 AAS Core 规模最大但实际价值取决于其‘不排名’的定位；OpenRig 和 Brigade 更接近可落地的产品工作流；NVIDIA Skills 提供官方能力治理的参考样本，值得作为面试与作品集素材。整体质量中上，但多数项目仍缺测试或安全边界证据，读者应优先做小范围可验证实验。

### 1. sickn33/agentic-awesome-skills · 73.0/100
https://github.com/sickn33/agentic-awesome-skills

- **一句话**：一个收录 2700+ 个可安装 SKILL.md 的 Agent 技能库，配套本地 CLI、MCP 和 Workbench，用于发现、审查与规划技能栈。
- **解决的问题**：Agent 技能散落在各仓库，读者难以发现、审查和复用一套完整可复现的技能组合。
- **独特之处**：把技能目录、Agent 自选、技能栈校验与变更前预览整合为一个本地控制面，并明确 Core 不负责推荐排序。
- **为什么有价值**：它示范了技能库最核心的产品问题不是‘收录多少’，而是权限边界、可审查性和可复现安装。
- **与你的关系**：当下可用它做一次技能目录调研，理解 Agent Skill 的发现—审查—安装链路；未来可把‘技能治理’作为作品集中的架构主题。
- **建议动作**：安装 CLI 并运行一次目录搜索，挑 2 个相关技能，完整阅读其 SKILL.md 并用预览模式生成一次变更计划。
- **Star 原因假设**：假设：Star 高增长来自‘技能库一站式聚合’的强发现需求，而非项目成熟度；支持信号是 48119 Star 与 2700+ 技能的目录规模；假设：多 agent 工具（Claude Code、Codex、Gemini CLI）的兼容标签扩大了受众面
- **风险/限制**：项目明确说 Core 不排名或不推荐技能，默认目录本身不提供质量筛选；README 注明 apply 与 recovery 仍为实验性，生产使用需谨慎；大量第三方技能的安全性、许可证与兼容性无法从元数据保证
- **判断置信度**：medium

### 2. mvschwarz/openrig · 72.0/100
https://github.com/mvschwarz/openrig

- **一句话**：用 YAML 定义由 Claude Code、Codex 等 coding agent 组成的持久化团队，提供带角色、共享上下文和任务归属的多 Agent 编排。
- **解决的问题**：多个 coding agent 并行工作时，会话、上下文和任务归属容易碎片化，难以作为团队持续协作。
- **独特之处**：把多个 harness 包装成可配置、可复用的‘rig’，由 lead agent 协调专家并汇报需要人类决策的事项。
- **为什么有价值**：它把多 Agent 从‘多个终端窗口’提升为有角色与共享状态的系统，直接对应 Agent 工作流的产品化难点。
- **与你的关系**：当下可观察它如何用 YAML 和 TUI 表达团队结构与任务归属；未来可借鉴到多 Agent 协作产品的状态与权限设计。
- **建议动作**：按 quickstart 在示例仓库中运行一个最小 rig，加入 2 个 agent，记录一次任务分配与结果回收过程。
- **Star 原因假设**：假设：Star 增长来自‘多 Agent 团队’叙事与 Claude Code/Codex 生态热度；支持信号是 7998 Star、npm CLI 与每日约 89 的观测增量；假设：作者‘AI civilization experiments’的公开叙事带来关注
- **风险/限制**：README 承认是个人实验衍生，长期维护与产品稳定性存疑；缺少测试信号，多 Agent 编排的正确性与故障恢复难以验证；多 agent 共享上下文可能放大权限和敏感信息泄露风险
- **判断置信度**：medium

### 3. escoffier-labs/brigade · 69.5/100
https://github.com/escoffier-labs/brigade

- **一句话**：为多个 coding agent 提供共享的工作记录、任务认领、验证凭据与跨工具记忆，基于本地文件运行，无守护进程。
- **解决的问题**：不同 Agent 工具之间无法可信地传递‘做了什么、是否验证通过、上下文在哪’，导致重复劳动与不可审计的声称。
- **独特之处**：以验证收据、运行日志和证据包为核心，让 Agent 之间可以核对真实退出码而不是相信‘测试已通过’。
- **为什么有价值**：它把 Agent 工作流最容易被忽视的‘可审计交接’作为产品核心，适合做 Agent 可靠性的产品思考素材。
- **与你的关系**：当下可研究其证据包与任务认领模型；未来可把‘Agent 交接与验证’作为作品集中的可靠性主题。
- **建议动作**：安装 CLI 并跑通一次最小交接示例，观察一条验证收据如何在不同 Agent 之间被读取和核对。
- **Star 原因假设**：假设：关注来自‘多 Agent 安全交接’的真实痛点，而非 Star 规模；支持信号是详尽的证据包文档与本地优先设计；假设：Claude Code/Codex 生态中缺乏可信交接机制，形成差异化发现需求
- **风险/限制**：Star 与社区信号很低，用户规模与长期维护不确定；92 个 open issues 相对 79 Star 偏高，可能说明问题多或反馈渠道集中；多工具记忆同步涉及权限与敏感数据边界，需自行评估
- **判断置信度**：medium

## 今日重点

重点看 OpenRig：目标用户是把多个 coding agent 当团队使用的开发者与 AI 产品经理。待办任务是让 Claude Code、Codex 等 agent 在共享上下文中分工协作并保留任务归属。旧替代方案是手动开多个终端、复制上下文、人工汇总结果，容易丢状态。价值主张是用 YAML 定义团队、由 lead agent 协调专家并汇报需人类决策的事项，把碎片会话变成持久组织。AI 是否必要：多 agent 协调本身是模型能力问题，AI 必要；但‘角色与任务归属’的建模是产品设计问题，不应默认交给模型自由发挥。核心指标可设为：一次任务从分配到验证通过的周期、上下文重复率、需人工介入次数、交接失败率。主要风险是项目偏个人实验、缺测试、共享上下文带来权限与敏感信息边界问题。一个作品集衍生想法：设计一个‘多 Agent 任务交接看板’，只展示任务归属、验证状态与阻塞点，用 OpenRig 或类似编排器做底层，重点评估交接失败率。
