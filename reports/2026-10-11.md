### 1. mvschwarz/openrig · 73.0/100
https://github.com/mvschwarz/openrig

- **一句话**：OpenRig 是一个开源多智能体编排 harness，用 YAML 定义由 Claude Code、Codex 等异构编码智能体组成的团队，以一个 lead agent 协调 specialists，把多个终端会话变成有角色、有共享上下文、有归属任务的持久团队。
- **解决的问题**：单个编码智能体缺乏跨会话的项目记忆与分工，用户想把不同模型/工具组合成一个可控团队时，只能手动开多个终端、复制上下文，协作成本高且状态易丢失。
- **独特之处**：把「harness 之上再包一层 rig」抽象成 YAML 配置的团队定义，混合 Claude Code 与 Codex 于同一系统，并提供 TUI 观察每个 seat 的运行时、模型、上下文与状态。
- **为什么有价值**：对 AI 产品经理而言，这是理解「多智能体编排」产品形态的清晰样本：如何定义角色、如何管理共享上下文、如何把不可见的编排过程做可视化。文档与引导路径较完整，适合作为学习与作品集参照。
- **与你的关系**：当下：阅读 getting-started 与 TUI 设计，理解多 agent 团队的状态管理与协调抽象。未来：可作为设计「面向团队的多智能体工作台」产品时的竞品/架构参考，或用作 demo 中编排层的实现。
- **建议动作**：30 分钟内读完 docs/reference/getting-started.md，画出一张 OpenRig 的「配置→启动→协调→结果」流程草图，并标注你认为对 AI PM 最关键的 2 个决策点。
- **Star 原因假设**：多智能体 + 混合 Claude/Codex 的定位契合当下编码 agent 团队化趋势，容易被开发者和 AI 工具爱好者转发（支持信号：topics 覆盖 multi-agent、agent-orchestration，且有 Discord/博客外链）；作者自称是 AI civilization 实验的开源系统，个人叙事带来关注度（支持信号：README 提及个人实验与 X 账号）；缺少历史快照，当前星数为 first_run_proxy，增长原因无法证实，仅为假设
- **风险/限制**：依赖 tmux 与特定 Node 版本，Windows 需走 WSL2 且自动化测试在 WSL2 未跑通，环境门槛高；无历史动量快照，stars 不足以证明真实使用量与留存；编排层抽象复杂，产品文档尚未验证大规模多人协作场景；安全边界与远端信任模型在 README 中未充分展开
- **判断置信度**：medium

### 2. morluto/rea · 67.0/100
https://github.com/morluto/rea

- **与你的关系**：当下：阅读 docs/mcp-contracts.md，观察它如何为专业工具设计 MCP 接口与技能边界。未来：在设计面向专业用户（安全、数据分析、金融合规）的 agent 技能时，可复用它的分层封装思路。

### 3. creedants/pstack-t3 · 64.0/100
https://github.com/creedants/pstack-t3

- **一句话**：pstack-t3 把 Lauren Tan 的 pstack 精工工作流移植到 T3 Code，让任意模型都能主导开发、由另一模型家族评审，并新增 brigade——每项目一个常驻协调者，在独立 git worktree 中运行工作单元，经合并队列落地主干。
- **解决的问题**：AI 编码代理产出过多「slop」且缺少审慎工程纪律，多模型并行协作时缺乏统一的评审、合并与协调机制，容易产生未审查就上主干的风险。
- **独特之处**：把「先复现 bug、先定设计、证明改动有效、交给其他模型打破」这套精工流程固化为可复用 agent skill，并用 brigade 协调者 + 单写者合并队列保证唯一写入主干。
- **为什么有价值**：这是把「工程纪律」产品化为一组 agent skill 的罕见样本，尤其对想学习如何设计可审计、可回滚、带人工审批点的多 agent 工作流的 AI PM 很有参考价值。
- **与你的关系**：当下：阅读 docs/how-it-works.md 理解 brigade 的协调者与队列抽象。未来：在设计带评审门禁的多 agent 交付流程时，可直接借鉴它的 worktree 隔离 + 单写者落地模式。
- **建议动作**：30 分钟内读完 docs/how-it-works.md 与 docs/live-runs.md，写下「协调者—工作单元—评审—落地」四步中你认为最容易被滥用的一个环节及原因。
- **Star 原因假设**：pstack 在 Cursor 社区已有认知度，移植到 T3 Code 且支持多模型评审，吸引关注（支持信号：README 明确标注上游 pstack 版本与 Cursor 源）；有自动化 CI、release 与 live runs 记录，可信度感知较好（支持信号：CI badge 与 live-runs 文档）；作者为个人/小团队项目，stars 处于长尾水平，热度主要来自小众工程圈
- **风险/限制**：stars 极低（4），社区验证与生态几乎为零，长期维护不确定；无安全相关信号（has_security=false），隔离与权限边界未在 README 说明；依赖 T3 Code 环境，脱离该工具难以复用
- **判断置信度**：low

## 今日重点

重点项目：mvschwarz/openrig。目标用户：同时使用 Claude Code、Codex 等多个编码 agent、希望把它们组织成有角色分工团队的开发者与 AI 工具探索者。待办任务：把散落在多个终端会话里的 agent 变成一个有共同上下文、能分工、产出可追踪决策的持久团队。旧替代方案：手动开多个终端、复制粘贴上下文、靠人脑维护谁在做什么，或用单一 harness 单打独斗。价值主张：用 YAML 定义团队、一条命令启动，lead agent 协调 specialists 并把需要人拍板的决策集中呈现；TUI 可视化每个 seat 的模型、上下文与状态。AI 是否必要：是——协调、上下文汇聚与多模型评审本身就是 LLM 能力的产品化，不是简单脚本。核心指标：一次任务从请求到可交付的完成率、人工干预频次、跨模型评审命中问题比例、上下文丢失率。主要风险：环境依赖重（tmux、特定 Node 版本、WSL2 测试未覆盖），无历史动量证据，编排层复杂且安全边界未展开。作品集衍生想法：做一个「多智能体协作可视化复盘面板」，把 OpenRig 这类编排的运行日志转成一张「谁在何时做了什么决策」的时间线，作为 AI PM 对多 agent 协作可解释性的作品。
