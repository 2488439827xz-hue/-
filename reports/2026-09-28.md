### 1. noteflowai/dsh-skills-anywhere · 82.2/100
https://github.com/noteflowai/dsh-skills-anywhere

- **一句话**：把本地和 Git 来源的 Agent Skills 聚合为一份目录，并可通过 DeepSeek Harness 或本地 stdio MCP 按需加载；核心命令可在加载前检查 SKILL.md 引用的本地资源是否缺失，并可作为 CI 门禁。
- **解决的问题**：Agent Skills 在不同工具（Claude Code、Codex、Cursor、Gemini CLI）间迁移或复用前，常出现本地引用/伴随文件缺失，导致技能安装后在运行时才失败，缺少加载前的静态检查。
- **独特之处**：把「技能可移植性」变成一个可执行、可进 CI、可输出 JSON 的检查动作，并明确声明只检查本地 Markdown 链接目标、不执行技能、不检查散文依赖，边界诚实。
- **为什么有价值**：对 AI 产品管理读者而言，它示范了技能分发中「确定性校验层」该怎么做：先证明资源齐全，再进模型执行。这种把不可靠资产变成可验证流程的思路，比再收藏一个技能清单更有迁移价值。
- **与你的关系**：当下用途：在你自己的 ~/.agent-skills 目录上跑 check 命令，理解 Agent Skill 的「依赖面」到底包含什么。未来用途：把资源检查融入团队技能仓库的 PR 门禁，或写进你关于「Agent 技能供应链质量」的作品集分析。
- **建议动作**：30 分钟内：npx --yes dsh-skills-anywhere@0.16.0 check 一个已有 SKILL.md 的路径并加 --resources --json，记录输出；再把它接进一个本地测试脚本，观察 --fail-on-resource-issues 如何改变退出码。
- **Star 原因假设**：假设：DeepSeek Harness 与 MCP 双集成切中了多工具用户的实际分发痛点，支持信号是 README 同时提供 dsh provider 与 stdio MCP 两种加载路径；假设：CI 门禁（--fail-on-resource-issues）对团队用户有吸引力，支持信号是仓库有 CI workflow 与 npm 包、OpenSSF Scorecard 徽章；假设：文档提供「无需 clone 的首次检查」教程，降低了尝鲜成本，支持信号是 docs/first-resource-check.md 与三个 pinned 公共示例
- **风险/限制**：仓库仅 6 star、社区反馈极少，长期维护与案例积累不确定；README 明确只检查本地 Markdown 链接目标，不检查散文依赖、不执行技能，实际防护范围有限，容易被误解为完整安全扫描；对 DeepSeek Harness 的依赖若上游不稳，集成路径可能变化
- **判断置信度**：medium

### 2. IvoryCanvas/QAMap · 77.5/100
https://github.com/IvoryCanvas/QAMap

- **一句话**：本地优先的 CLI，读取当前分支、仓库结构与已有测试，把 PR diff 转成行为生命周期与 QA 场景，回答「哪些行为可能受影响、哪些正常/失败/边界/状态迁移场景要测、哪些文件行符号支撑该判断」，并可路由已有验证命令或准备自动化草稿。
- **解决的问题**：PR 合并前缺乏结构化的 QA 计划：人看 diff 凭经验猜测试点，容易漏掉用户流程、状态迁移与失败路径，且很难把判断与具体代码证据对应起来。
- **独特之处**：用确定性的本地静态分析生成「有证据支撑的测试计划」，明确不做 LLM 调用、不上传源代码，并提供 agent brief 让宿主 Agent 复用已有分析而非重建 diff。
- **为什么有价值**：它把「AI 在流程中该做哪一步、不该做哪一步」讲清楚：分析是确定性的，LLM 只在宿主侧。这对学习 AI 产品管理的人是一个很好的「AI 非必要性判断」案例。
- **与你的关系**：当下用途：在你自己的仓库分支上跑 qamap qa，观察它列出的待验证场景与你的直觉差异。未来用途：把它的输出格式当作设计「评审前检查清单」类 AI 功能的模板，或写一篇对比「LLM 猜测试点 vs 静态分析给证据」的作品集文章。
- **建议动作**：30 分钟内：在任意有测试的仓库分支执行 npx --yes @ivorycanvas/qamap@latest qa，阅读 Change 与 Verify before merge 两栏，挑一个场景与 diff 证据对照，判断它的建议是否成立。
- **Star 原因假设**：假设：它绑定在已有的代码评审工作流上，容易在开发圈口口相传，支持信号是已有 npm 包、OpenAI 插件目录入口与 CI 徽章；假设：「零 LLM、本地优先」的定位减少了隐私与成本顾虑，支持信号是 README 明确不调用 LLM、不上传源码；假设：agent brief 与 token 结果等 release notes 提供了可验证的收益信号，支持信号是 docs/releases/0.5.1.md 有实测 token 数据
- **风险/限制**：静态分析对动态语言与运行时行为的影响判断可能有遗漏，误报/漏报概率未在证据中说明；证据中 readme_signals 显示无 tests、无 security 章节，代码质量保证程度难以确认；体量小、社区信号弱，长期维护存在不确定性
- **判断置信度**：medium

## 今日重点

重点项目：noteflowai/dsh-skills-anywhere。目标用户：同时使用 DeepSeek Harness、Claude Code、Codex 等多种 agent 工具的开发者，以及要把技能沉淀进团队仓库并做 CI 门禁的技术负责人。待办任务：在把一份 Agent Skill 迁移、复用或上线前，确认它依赖的本地资源（Markdown 链接目标、伴随文件）是否齐全，避免安装后运行时才发现缺失。旧替代方案：手动打开 SKILL.md 逐个点链接、凭经验判断，或直接安装后靠报错发现；团队里通常没有加载前检查工具。价值主张：把「技能可移植性」做成一条可脚本化、可进 CI、可输出 JSON 的确定性检查，并明确不做执行、不查散文依赖。AI 是否必要：这里恰恰是「AI 非必要」的好例子——静态资源检查不需要 LLM，确定性反而带来可复现与可审计；AI 只在后续按需加载技能时发挥作用。核心指标：CI 中 --fail-on-resource-issues 的拦截次数与首次检查通过率、技能跨工具复用时的资源缺失率、从 clone 到完成首次检查的时间。主要风险：产品边界窄、社区反馈极少，维护可持续性未知；名字里的 DeepSeek Harness 使其看起来绑定单一宿主，实际 MCP 路径的通用性需自行验证；检查范围有限，不能被当成安全审计。作品集衍生想法：做一份「Agent Skill 供应链体检」报告模板——对 5 个流行技能分别跑资源检查与引用完整度统计，给出可量化的可移植性排名，并配一份 10 分钟落地教程。
